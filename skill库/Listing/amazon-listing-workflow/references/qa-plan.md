# QA 选题与人工筛选候选稿

默认交付10条完整Q/A，供用户人工选择、修改。信息未确认不阻止拟稿，不再只交1条已验证QA或把其余9条变成无答案的问题清单。用户仅要求修改Skill时更新规则，不自动重写整套Listing。

## 选题与埋词

读取关键词库、词根库、本品事实、当前Listing和竞品五点。关键词/词根与竞品五点任一来源即可启发选题，不要求两类来源同时支持每题。

先规划10个不同的购买疑问：从关键词原短语和词根属性中的场景、用途、人群、材质、规格、操作提炼问题；也可把竞品五点的特点、利益、操作或使用边界转成问题。保留关键词ID/词根ID或竞品ID、原点序号与原文来源；不能把竞品信息登记成本品确认事实。

沿用原精准等级：绝对精准优先，其次相对精准，再考虑其他适用等级。自然融入原关键词或组合词根，不为精确命中牺牲语法。五点和QA可用必要连接词，不受标题全部词语来自词根库的限制。

优先补充正文未展开的问题。已有内容可以转成更具体的场景、操作或决策问答；必要时允许FAQ复述核心信息，并注明overlap，不再将“必须全部新增事实”作为生成10条的门槛。10条之间仍需问题独立，不能换问法重复凑数。

## 答案与状态

每题都直接拟写可供编辑的答案，不能仅写“待确认”“请联系客服”或空白占位。按依据标记：
- confirmed：本品已确认资料支持，列fact_ids
- inferred：从常规使用逻辑提出的建议或推断，标明推断部分和待核实事项
- unconfirmed：参考竞品或拟定本品可能具备的用途/属性写出的候选答案，标明假设与待核实事项

后两类无需先提问用户或等确认再生成。可以拟写假设性答案，但不能与已确认事实相冲突，不能假称测试、认证或竞品数据已经属于本品。用户已说明“没有测试”时不生成“已通过测试”的答案。具体缺少的数值不随意编造；可改写为条件式使用建议或不依赖该数值的答案。

交付时整体注明“10条人工筛选候选稿”，每题旁显示“已确认/推断建议/待确认”及简短核实提示，不能只把状态藏在JSON。question与answer保存目标语言原文；HTML交付另配对应的中文问题和答案。状态及review_note用用户语言单独显示，不混入任一语言的拟发布答案；翻译须保留推断或待确认边界。仍需写出具体Q/A，而非用状态说明替代答案。

## 长度与格式

Q≤100、A≤250字符，含空格与标点，不含外部编号及审核标签。一问一事，先回答，再说明用途、建议或必要条件。审阅提示单独计数。10条均为商家拟稿，不伪装成真实买家问答，不自动发布。

## 记录与完成

qas_delivery_mode默认review_candidates，每条保存question、answer、evidence_status、review_note、fact_ids、source_refs、keyword_ids/root_ids、gap、overlap。source_refs至少保留一个实际关键词/词根/竞品来源；gap允许记录“核心信息复述”并在overlap指明已有位置。未确认项的fact_ids可以为空，不捏造证据。

10条完整候选及标记交付后，QA生成阶段记done、output_kind=draft、review_status=pending_user_review；不能再因未确认而标记“缺9条QA”。这只表示候选生成完成，不等于事实已核实或适合直接发布。用户选择、修改并确认后再记录selected/approved状态。用户明确要求可直接发布的核实稿时才使用verified模式；该模式不得将未确认答案标为合格。

复查数量、长度、选题来源、题间重复、标签可见性及已知事实冲突。运行scripts/check_copy.py检查数量、长度和状态字段；语义与证据人工复查。标题/正文变化后更新overlap即可，不因主题已出现而自动删除候选。

## 与ST和购物问答的衔接

当前已有候选QA直接参与本次ST去重，记录qas_delivery_mode和版本；ST按现有内容生成并立即输出，不等待QA筛选或修改。后续实际需要更新时再基于新内容生成新版ST。未经确认的QA假设不能成为ST或其他商品字段的新事实依据。不宣称QA数量或关键词写法保证Alexa抓取、推荐或搜索收录。
